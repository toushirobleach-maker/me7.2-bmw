# Как работать со стоком SP-Daten и своей машиной

## Что за BIN включён в репозиторий

Это аналитическое объединение `7532675A.0PA` (program) и `G7533626.0DA` (data) из E53/EK726, с EPK6901I41D. Непокрытые адреса заполнены FF. Покрыто489750 из524288 байт. Включённый файл имеет37/38 checksum: ROMSYS parameter endpoints хранит0000971D, а по реконструкции получается00015A59. End marker калибровок отсутствует.

**Этот файл нельзя напрямую отправлять как полный образ чипа или брать из него весь64-КиБ сектор.** Неизвестные участки не становятся настоящими данными от заполнения FF. `checksums.py fix` может согласовать математику с этими байтами, но не восстановит недостающее содержимое.

В проверенной паре .0DA не покрыты:

| File range, конец не включён | Размер |
| --- | ---: |
| 1FC1E..1FC66 |72 байта|
| 1FCC0..20000 |832 байта|

Всего904 байта cal, включая служебный хвост и marker. Не добавлять marker по чужому дампу или предположению; нужен собственный полный и целостный источник.

## Нужно ли «поправить сток под машину»

Нужно различать четыре задачи:

1. **Выбор совместимого ПО и варианта.** Проверяются аппаратный номер DME, допустимый ZUSB/программа, двигатель, КПП, рынок и комплектация. Совпадение EPK не доказывает правильность всего варианта. Для известной DAT-строки сборочный ZUSB=7533625,HW=7532675,program=7532675A.0PA. `G7533626` — конкретный E53/M62B44LEV/5HP24 набор, а не универсальная прошивка всех M62 или L322.
2. **Получение полного содержимого.** В SP-Daten есть диапазоны обновления, а не обязательная копия всех физических байтов. Для cal-only переноса нужны собственные непокрытые байты из verified baseline.
3. **Кодирование и сервисная идентификация.** VIN/UIF и варианты кодирования обрабатываются соответствующим сервисным процессом. Ручная вставка VIN в произвольный BIN не заменяет подбор варианта и кодирование.
4. **EWS/ввод заменённого блока в эксплуатацию.** Это отдельная задача совместимости и согласования. Для EWS3.3 одинаковый VIN не означает одинаковую rolling-code table; alignment не является универсальным превращением чужого б/у DME в совместимый блок. Подготовщик ниже EWS/ISN не переносит и не отключает. О принципе разных таблиц: [учебный материал BMW EWS](https://www.ge39.com/files/EWS.pdf).

Для родного совместимого DME корректный заводской data-set не требует произвольного редактирования карт «по VIN». Для замены/пересадки блока или изменённого двигателя могут понадобиться другие работы; универсального набора байтов «под любую машину» этот репозиторий не задаёт.

## Путь A: штатное полное программирование

Для реального восстановления заводских program+data использовать подходящий OEM-процесс программирования с исходными SP-Daten, например соответствующую среду WinKFP для поддерживаемого BMW. Сначала определить допустимый ZUSB/вариант и план операции, обеспечить питание/связь и предусмотренный способ восстановления. Не подавать аналитический BIN вместо требуемых .0PA/.0DA. Идентификация/кодирование/EWS выполняются по штатной процедуре именно этого автомобиля и блока.

Наш Python writer **не реализует полную запись512 КиБ**, замену программного кода или восстановление загрузчика. Смена program-версии, аппаратной ревизии и полное возвращение к заводскому коду через него не выполняются. Эта инструкция не заявляет аппаратного испытания полного stock restore.

## Путь B: только заводские калибровки при уже совместимой программе

Добавлен [prepare_stock.py](../05_tools/prepare_stock.py), всегда офлайн. На вход подаются собственный полный512 baseline и собственные matching .0PA/.0DA. Парсер проверяет каждую запись, поддерживает наблюдаемые data-types00/10, ELAR04 и нулевой segment02. Неизвестные расширения и конфликтующие записи отвергаются.

Алгоритм:

- Проверить profile и все38 checksum собственного baseline.
- Проверить, что все известные program bytes .0PA совпадают с baseline. При отличиях остановиться; cal-only запись не исправляет программу.
- Наложить только реально присутствующие байты .0DA в cal.
- Сохранить непокрытые байты собственного baseline, включая его marker. В этой компоновке отдельно сохраняются известные поля идентификации1FD26..1FD43 и UIF/reserved1FD54..1FFFB. Это не полная карта всех индивидуальных данных ECU.
- Пересчитать checksum и проверить их независимо; потребовать отсутствие изменений вне cal.
- Сохранить отдельный кандидат и JSON с SHA, покрытием, preserved-полями, diff и ограничениями.

Пример полного процесса, выполняемого самим владельцем. При подготовке репозитория эти аппаратные команды не запускались:

```sh
# 1. Собственный свежий baseline; двигатель заглушён, зажигание II.
.venv/bin/python -u 05_tools/read.py --kind flash --port /dev/cu.usbserial-YOUR_CABLE --output runs/my_current_512KiB.bin --execute

# 2. Только офлайн; пути к SP-Daten принадлежат пользователю.
python3 05_tools/prepare_stock.py --baseline runs/my_current_512KiB.bin --program local/sp_daten/program.0PA --data local/sp_daten/calibration.0DA --output runs/stock_cal_candidate_512KiB.bin

# 3. Проверка результата и просмотр отдельного JSON/diff.
python3 05_tools/verify.py runs/stock_cal_candidate_512KiB.bin

# 4. План записи, без открытия порта.
python3 05_tools/write.py runs/stock_cal_candidate_512KiB.bin --baseline runs/my_current_512KiB.bin

# 5. После проверки совместимости/питания: только сектор cal64.
.venv/bin/python -u 05_tools/write.py runs/stock_cal_candidate_512KiB.bin --baseline runs/my_current_512KiB.bin --port /dev/cu.usbserial-YOUR_CABLE --execute
```

Writer ещё раз читает текущую flash и требует exact baseline. После записи/native checksum он запросит физический цикл зажигания и полностью перечитает512 КиБ. Успех — `SUCCESS_EXACT_FULL_IMAGE_MATCH`. Адаптации и ошибки автоматически не стираются; поведение двигателя, кодирование и EWS отдельно проверяются по сервисной процедуре.

Подготовленный overlay сохраняет существующий program и непокрытые области; его нельзя называть полной копией заводского чипа. Старые модификации в непокрытых областях могут сохраниться. Правильность checksum не доказывает выбор подходящей заводской комплектации.

## Публичные ограничения

В Git включён только исходный аналитический stock BIN. Нет донорских BIN, cal64, реальных transfer/security логов. Подготовка stock overlay испытана на синтетических данных; реальная полная stock-перепрошивка новым кодом не квалифицирована. Полный FR PDF и ссылки на него не распространяются.
