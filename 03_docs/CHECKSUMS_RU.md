# Проверка и исправление контрольных сумм

Поддерживается фиксированная структура 7532675 / 6901I41D. В полном образе проверяются **38 записей**: три ROMSYS, CRC32 и 34 multipoint-дескриптора. В MP-строке проверяются и сумма, и её инверсия; это одна запись из 38.

| Структура | Где хранится / что считается |
| --- | --- |
| ROMSYS startup | u32 LE @0x8038; сумма u16 @0x8000 и @0xFFFE |
| ROMSYS cal endpoints | адрес хранения из u32 @0x8010; границы из @0x8030/0x8034 |
| ROMSYS program endpoints | u32 @0x803C; граничные u16 страниц согласно ROMSYS |
| Multipoint | дескрипторы @0x17C7C, @0x17C8C и 32 записи @0x1EAA6..0x1EC96 |
| CRC32 | ISO-HDLC, байты `[0x10000:0x1FC04]`, хранится u32 LE @0x1FC0E |

MP-дескриптор — четыре u32 LE: start CPU, end CPU включительно, sum, inverse. Суммируются u16 LE, результат modulo 2^32. start=end — пустая запись с суммой 0. Профиль фиксирует все границы, чтобы повреждённый указатель не превратился в «новую checksum».

## Порядок исправления

1. Проверить размер, EPK, ROMSYS-указатели и границы всех MP.
2. Пересчитать три ROMSYS.
3. Привести все MP-пары sum/inverse к канонической валидной паре `0 / FFFFFFFF`.
4. Пересчитать MP и заполнить sum/inverse.
5. Пересчитать CRC32 последним.
6. Проверить результат независимым путём: массив u16 и побитный CRC вместо struct/zlib.

Шаг 3 необходим, потому что диапазон `817A60..817CA5` включает собственную пару checksum, а другие диапазоны включают соседние пары. Сумма четырёх u16 любой правильной пары u32 sum/~sum всегда **0x1FFFE**. Исправление произвольно повреждённых хранимых сумм без нормализации может исказить результат. Алгоритм отдельно проверяет, что диапазоны включают пары целиком либо не включают их вовсе.

Тесты портят все checksum-поля одновременно, отдельные самовключённые пары, байты кода и калибровок, проверяют CRC-вектор `123456789 → CBF43926`, идемпотентность и изменение только разрешённых полей. Пересчёт не меняет исправляемый байт данных; он меняет сумму для выбранных данных.

## Найденное ограничение стока SP-Daten

В неизменённом `00_stock/...bin`:

- SHA-256: `5ec2443311b6173e4f0bb770eb1f84c0a15a270d3bd6ac52648a77d450db5dd9`.
- Проходят 37/38 записей: CRC32, 34 MP и две ROMSYS.
- ROMSYS parameter endpoints: хранится `0x0000971D`, по реконструированным байтам получается `0x00015A59`.
- Файл заканчивает cal байтами `FFFFFFFF`; в дампе машины @0x1FFFC находятся `5A A5 C3 3C`.
- EXTRACT_REPORT фиксирует неполное покрытие исходными блоками: 489750 байт из 524288. Это реконструкция с заполненными промежутками.

Файл не изменён. Не следует автоматически вставлять маркер по аналогии и называть результат подтверждённым стоком. `checksums.py fix` может сделать математически согласованный отдельный файл, но не восстанавливает покрытие или происхождение. Writer отдельно требует проверенный end marker и запрещает программные отличия от фактического baseline.

В историческом частном испытании три car-derived образа проходили все38 записей; сами образы/сырой эксперимент не распространяются. Публичные тесты используют искусственные fixtures. [Машинный аудит](../04_reports/REPOSITORY_AUDIT_CURRENT.json).

## Чего checksum не доказывает

Полноту IROM/EEPROM, заводское происхождение, правильность адресов калибровок, физическую корректность настроек, возможности boot recovery и безопасность полного flash. Запись кодовых областей не реализована даже если их checksum можно пересчитать офлайн.
